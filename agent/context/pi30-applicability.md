判定は 2 軸である。**判定** は機構の有無、**導入** は採用状態を示す。

- **判定 = 完全**: 機構が repo に存在し、決定論的テストまたは検証コマンドで固定されている。
- **判定 = 部分**: 機構の一部のみ、ホスト所有、既定 off、または近似。過大主張を避けるため「完全」とは書かない。
- **判定 = 欠落**: 機構が repo に存在せず、ホスト機能の設定点も無い。
- **導入 = 完全導入 / 部分導入**: 採用済み（部分導入は意図的な差分・既定 off を含む）。
- **導入 = 保留**: 前提条件（評価基盤・ホスト API・予算）待ち。
- **導入 = 不採用**: 採用しない（安全・コスト・重複のいずれかを理由とする）。

**実装済みと検証済みは別である。** 下の「1.2 検証マトリクス」を参照。

判断基準は「Harness Tax（常時ロード・実行時間・外部依存の総コスト）を増やさず、
既存の決定論ゲートで検証できるか」。30技術すべてを一律に足すのではなく、
既に同等の機構があるものは重複実装しない。

## 2. 今回の実装: AHE change manifest (#16)

### 2.1 何が欠けていたか

Harness² の失敗 trace は `{signature, task, target, message}` のみで、
「その失敗を引き起こした変更集合」を持っていなかった。AHE (arXiv:2604.25850) は
harness への変更を `change_manifest.json`
（`manifest_version` / `iteration` / `changes[]`（各 `file_path`・`failure_evidence`・`root_cause`・
`predicted_impact`）/ `verification`）として記録し、次回評価で変更単位に keep/revert を
判定する。本実装はそのうち **file_path 集合のみ**を trace に付与する。
上流実装 `china-qijizhifeng/agentic-harness-engineering` の `evolve.py`
（`load_change_manifest` / `archive_change_manifest`）と `references/HARNESS.md` を
clone して確認した（2026-11-22）。

### 2.2 実装

| 層       | ファイル                                                       | 変更                                                                                                                                                                                                                                                                                           |
| -------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| producer | `agent/harnesses/omp/extensions/lib/mission-bridge.ts`         | `EvolutionTrace.manifest?: string[]`、`MAX_TRACE_MANIFEST=32`、`MAX_TRACE_PATH_CHARS=300`、`sanitizeTraceManifest(root, paths)`。repo 相対・allowlist 検証・重複排除・ソート後に上限適用。`appendEvolutionTrace` でも正規化し、空 manifest を省略。書込みは record のバイト数を含めて cap 判定 |
| producer | `agent/harnesses/omp/extensions/sol-pi.ts`                     | `recordTrace` が Action Fusion の edit/write 呼び出しで追跡したファイル（ツール結果あたり最大20、セッション最大512）と失敗 target を manifest として記録。target 用に 1 枠を予約。shell 経由の変更は観測しない                                                                                 |
| consumer | `agent/scripts/evolve/harness2-offline.py`                     | `parse_manifest` が型・件数・target allowlist を fail-closed 検証（33件以上・300文字超は rc=2）。クラスタに `manifests`（union + ソート）を追加し、`EXPERIENCE.md` の evidence に `manifest: path,...` を記載（先頭5件 + `+N`、300文字予算でパス境界のみで省略）                               |
| tests    | `agent/harnesses/omp/extensions/lib/sol-pi.test.ts`            | sanitize の正規化・境界、sort-before-cap、append の manifest 正規化・空省略・byte cap                                                                                                                                                                                                          |
| tests    | `agent/harnesses/omp/extensions/lib/continual-harness.test.ts` | in-process mirror の manifest union と Python parity（32/300/不正値）                                                                                                                                                                                                                          |
| tests    | `agent/scripts/test-harness2-offline.sh`                       | union/ソート/重複排除、EXPERIENCE 反映、32件受理・33件拒否、300文字受理・301文字拒否                                                                                                                                                                                                           |

manifest は **パスの集合のみ**（diff 本文やハッシュは持たない）。候補の差分は
Harness² の `new_text` が既に持っており、evolver が必要とするのは「どのファイル群が
同時に触られたか」の帰属情報だけである。32件上限と advisory 動作は Harness Tax を
増やさないための境界。trace ファイルは producer が 960 KiB (`traceMaxBytes`) で追記を止め、
consumer の 1 MiB 読取り上限より小さく保つ（単一 record の超過も書かない）。

### 2.3 使い方

```bash
# 失敗 trace は従来どおり自動蓄積される。manifest が付く。
jq -c 'select(.manifest)' ~/.claude/session-data/swarm/evolve-traces/*.jsonl | head

# クラスタ単位の変更帰属を見る
python3 -I -B agent/scripts/evolve/harness2-offline.py \
  --traces ~/.claude/session-data/swarm/evolve-traces/<repo>.jsonl \
  --candidates cands.json --repo-root . --experience agent/context/library/EXPERIENCE.md \
  --out-dir .claude/mission-prop --json | jq '.clusters[] | {signature, manifests}'
```

## 3. 見送り判断の詳細

- **#12 埋め込み検索 / #17 FTS5/BM25 / #22 埋め込み記憶**: 既存の構造検索
  (trail / codegraph / ast-grep) と `repl_filter` の grep/slice で足りる。
  index のビルド・更新・メモリ・決定論性のコストが便益を上回る。
- **#19 RRSI / #26 圧縮 proxy / #30 subprocess 排除**: 安全性・分離・外部依存の
  いずれかを犠牲にする。ホスト側の ratchet（host-only）が既定 off である事実も尊重する。
- **#4 Codemode / #10 LCM DAG / #25 自律実験ループ**: ホスト API か、低分散の
  ベンチ対象が前提。repo 側で先回りして実装すると Harness Tax と保守負担だけが残る。
  前提が揃った時点で個別ミッションとして再評価する。
- **#6 mid-run steering**: ユーザーの直接入力が steering であり、追加 hook は
  二重制御になる。
- **#1 PACT の編集予算**: prefix cache の安定性を守る現行ゲートを優先し、
  プロンプト書換え回数の予算化は導入しない。
